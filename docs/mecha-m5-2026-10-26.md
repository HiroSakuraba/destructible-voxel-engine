# Iron Yard M5 — missions, checkpoints, complete restart and sound

This change builds on merged M1–M4 PR #235 without replacing its locomotion, combat or voxel AI architecture.

## Mission loop
A new optional `dve.prototype.mech_extraction` marker offers a second victory condition. With the marker absent, existing M1/M2 scenes still win on the authored target count. With the marker present, destroying the required hostiles arms extraction; the player must move into its configurable XY radius before winning. The generated Iron Yard places a visible green extraction pillar next to that marker. HUD mission telemetry and prompt report the current objective.

## F5/F9 checkpoint save/load
The existing DVE `GameSaveData::gameSections` field carries a new size-bounded `dve.prototype.mecha` section. It stores mecha-only deterministic controller state:

- Player motor position, velocity, leg and torso orientation, boost energy, health and game phase.
- Primary/secondary ammo and cooldowns; in-flight rockets, sequences, positions and velocities.
- Stable keyed enemy HP, turret aim, firing cooldowns, route-replan countdown, current path and waypoint.
- Mission extraction activation, telemetry counters and audio-event serial numbers.

World objects, destroyed voxel geometry, surface marks, physics bodies and timing remain stored in the existing world/game-runtime sections. The mecha parser is versioned (v1), capped at 64 KiB, validates every numeric range and key, cross-checks actor enabled flags and poses against restored world state, and commits controller fields only after a complete parse. A corrupt or missing game section fails load instead of silently resetting combat. `PlayerApp` already builds a fresh session before loading; failed loads keep the currently running world.

## Restart (R)
The mecha runtime captures a pristine world snapshot on startup. Restart now calls `GameWorld::restore_save_state` with that snapshot before resetting ammo, health, AI and objectives, restoring previously destroyed voxel cover and scenery as well as enemy poses. It also resets event sequences, so the audio driver can rebase without replaying earlier shots.

## Procedural sound
`dve_player` uses the existing `AudioMixer` and `SdlSynthAudioDevice`. A mecha audio driver registers five small synthesized, resident one-shot waveforms for autocannon, rockets, explosions, incoming fire and boosting. Each is triggered by bounded counters in `PrototypeHud::mechAudio`. All synthesis/sample allocation occurs once on the control thread; the mixer callback uses already resident voices. This requires an audio-enabled player build and working output device; headless and `--no-audio` runs remain silent.

## Regression suite
`dve_mecha_m5_tests` includes extraction gating, save/load and invalid-data rejection, destructible voxel cover restart, standalone exported Iron Yard `.dvesave` round trip and clean player re-load. Retains existing `dve_mecha_game_tests` and `dve_mecha_m3_m4_tests`.

## Deferred from M5
This is a compact mission loop, not a campaign/mission authoring system. No branching narrative, persistent profile progression, spatial audio, user-authored sound banks, multiplayer synchronization, or full third-person mech handling; those are separate future work.
